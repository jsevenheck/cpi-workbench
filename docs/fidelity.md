# Fidelity: what matches CPI and what does not (yet)

"To verify" means the behaviour follows SAP's documentation or Camel's code but has not been
observed on a tenant. The probes in [`probes/`](../probes/README.md) turn these items into facts.
Finding numbers (F…) and questions (Q…) refer to the [plan](plan.md).

## XSLT Mapping and XML tools

| Area | Status |
|---|---|
| Saxon release line (9.9) | Same line as CPI. CPI runs **EE 9.9.1.6** (probe, F51), the simulator **HE 9.9.1.8**. |
| Higher-order functions, `xsl:evaluate` | Not in HE 9.9; use the *Modern HE (Saxon 12)* profile. The error message says so. |
| Schema-aware XSLT, streaming | EE only; not available. The error message says that CPI supports it. |
| `format-date` with languages other than English | HE prints English names (`[Language: en]…`); CPI's EE localises them (`5. März 2026`, F51). A known gap. |
| Header vs. property with the same name | Header wins, as on a tenant (F51). |
| Declared parameter without header or property | The XSLT default is used, as on a tenant (F51); can be switched to "error". |
| Typed parameter values | Passed as Java objects, so Saxon converts them (F21); the probe gives the same types on a tenant (F51). `$exchange` prints as `Exchange[<id>]`, as on a tenant; the ID's shape is copied, its value is the simulator's. The implicit timezone is UTC (`PT0S`), as on a tenant. |
| Reflexive Java calls (`java:` namespaces) | Supported for JDK classes, since SAP's own samples use them (F32). Classes from the iFlow's jars are not available to XSLT. Argument conversion follows simple rules, not all of Saxon-EE's. |
| XSD validation | JDK validator, XML Schema 1.0. CPI's validator is **to verify** (Q-V1). |
| XPath tab | 3.1 (Saxon) by default, as SAP documents for the Content Modifier and Filter and as Router conditions in real iFlows need (F37). 1.0 (JDK) stays available; no CPI step is known to use it. |
| File access (includes, `doc()`, `unparsed-text()`, external entities, also in `parse-xml()`) | Inside the project folder only, no network: a simulator rule, standing in for the iFlow's resources. Whether CPI resolves external entities and DTDs is **to verify**. |
| `unparsed-text()` encoding | The encoding argument is used; without it, files are read as UTF-8 (the spec also allows guessing from the content). |
| `xsl:result-document`, `collection()` | Not supported (`UnsupportedInSimulator`); the simulator has no place for secondary results. What CPI does with them is **to verify**. |

## Flow Steps: Content Modifier, Filter, Router, Splitter, Gather, Converter

Camel Simple (Non-XML conditions and *Expression* values):

| Area | Status |
|---|---|
| Where CPI uses it | Router and Looping Process Call conditions with *Expression Type* Non-XML, and Content Modifier / Write Variables values of type *Expression* (SAP: [Using Camel Simple Expression Language](https://help.sap.com/docs/cloud-integration/sap-cloud-integration/using-camel-simple-expression-language)). The Content Filter also takes it; the simulator has no Content Filter. |
| Engine | A Groovy engine's own Camel evaluates the expression: 3.14.7, as a tenant runs both script versions (F48). Tenants on software 6.x / 5.x still run Camel 2 (SAP numbers 8.x / 7.x for Camel 3, F34, and is migrating tenants); the simulator does not cover them. OGNL calls such as `${in.header.fname.split(',')[0]}` (in SAP's table) work; both engines bundle `camel-bean` for them. |
| CPI spellings plain Camel rejects | SAP's Router table ([Define Router](https://help.sap.com/docs/r/368c481cd6954bdfa5d0435479fd4eaf/Cloud/en-US/d7fddbd52e3944d3a6d4e5b228c7e63b.html)) uses `=`, `and`, `or` and `${property.x}`. Camel has no `=` operator, and Camel 3 dropped `and`, `or` and `property`. The simulator rewrites them to `==`, `&&`, `\|\|` and `${exchangeProperty.x}` and the Router result shows the rewritten expression. CPI converts `property` to `exchangeProperty` itself (SAP patch notes, August 2024, 7.28.14 / 6.55.13). That it treats `=`, `and` and `or` exactly like `==`, `&&` and `\|\|` is an **assumption** (F35). |
| `${exchangeProperty.x}` | SAP's documentation uses `${property.x}` (180 times) and never `${exchangeProperty.x}` (SAP-docs repository, 2026-10-22). It works in the simulator. A [SAP Community post](https://community.sap.com/t5/technology-blog-posts-by-members/get-to-know-camel-s-simple-expression-language-in-sap-cloud-integration/ba-p/13292822) reportedly says it fails in a CPI Router condition (seen only in a search summary; the page could not be opened from the build environment). **To verify.** |
| Content Modifier expressions | SAP: it does not process equality or comparison expressions; operators stay text (Camel's expression parser). SAP lists a subset of Camel's functions for it; the simulator does not reject the others. |
| `${exception.…}`, `${exchangeId}`, `${date:now}` | There is no exception in the tester, so `${exception.message}` is empty. IDs and dates come from the simulator's run. |

The steps (SAP: *Define Content Modifier*, *Define Filter*, *Define Router*, *Define General Splitter*, *Define Iterating Splitter*, *Define Gather and Join*):

| Area | Status |
|---|---|
| XPath | Saxon-HE 9.9 (CPI's release line; Saxon 12 if 9.9 is not installed), XPath 3.1, in the XML engine: SAP documents XPath 3.1 for the Content Modifier, and Router conditions in real iFlows use XPath 2.0 syntax such as `/node()/*:IDOC` (F37). Namespace prefixes come from the namespace mapping (the iFlow's *Runtime Configuration*), shared with the XPath tab. The Router's XPath version is not documented; 3.1 is an assumption. |
| XPath variables | `$name` is the header of that name, else the exchange property: Camel's XPath variable resolver (`MessageVariableResolver` in Camel 3.14.7) does this, and real iFlows rely on it (`Student[Age > $AgeLimit_Header]`, `$NodeId="0"`; F39). Typed values (Integer, Boolean, …) become typed XPath values. Applies to Content Modifier XPath rows, Router XML conditions and the Filter. |
| Content Modifier rows | Run top to bottom (SAP); the header table before the property table, both before the body (SAP Community blog, seen only in a search summary: **to verify**). An XPath row reads the incoming body; with `$name` it sees the headers and properties of the rows above it. Constant values are not evaluated. *Data Type* is resolved by Camel, so `String` works as well as `java.lang.String`; a DOM type (`org.w3c.dom.NodeList`) keeps the XML as text. An XPath that returns several items gives the first one's string value: **to verify**. An empty body field leaves the body as it is: SAP does not say so, but most of SAP's sample Content Modifiers only set headers or properties and have an empty body (F38), which would otherwise erase the payload (an **assumption**). The body is Constant or Expression; Content Modifiers up to version 1.3 have no type and their body is an expression (F38). |
| Content Modifier sources the simulator lacks | Local and global variables: no variable store, so the *Default Value* is used, as CPI does when the variable is not found. Number Range and External Parameter: `UnsupportedInSimulator`. |
| Delete rows | The iFlow stores `$name=X` or `$include=pattern,$exclude=pattern` (F36); Camel's `removeHeaders` / `removeProperties` apply the patterns. That CPI uses these Camel methods is an assumption. |
| Filter | XPath 3.1 (SAP: Filter 1.1 uses XPath 3.1 EE); the result becomes the body, headers and properties stay. String joins the string values of all items (SAP's example: `10010`); Integer is that text as a whole number; Boolean is the effective boolean value; Node the first node; Nodelist all nodes one after another without a wrapper (SAP's examples). Integer, Boolean and Node follow Camel's XPath result types and the join has no separator (Camel's converter): **assumptions**. `function:simple('${…}')` (SAP's example) is replaced by the value Camel Simple gives, as an XPath string; that CPI treats it as a string is an assumption. |
| Router | Conditions run in the order of the gateway's outgoing flows in the iFlow (an assumption; the model has no order field), and the first true one wins. Routes that mix XML and Non-XML conditions are an error: SAP says the evaluation then fails. Without a match the default route is taken. With *Throw Exception* the simulator raises an exception instead; SAP only says that the default route must then end with *Terminate Message*, so this is an **assumption**. A condition that fails to evaluate is shown as an error. |
| General Splitter | Each message keeps the envelope of the **first** split point: its ancestors and, on every level, the siblings before it. Later siblings are dropped, and every split point goes under the first one's parent. This reproduces all of SAP's examples (`SplitStepTest`); other cases are inferred from them. |
| Iterating Splitter | Each message holds only the split point(s); with grouping above 1 they are concatenated (an assumption). *Token* splits at elements with that local name (CPI may use Camel's text-based `tokenizeXML`: **to verify**). |
| Line Break | General puts the first line in front of every message (SAP); Iterating does not. Like SAP's example, the text `\n` also counts as a line break. Messages have no trailing line break (**to verify**). |
| Splitter XPath | Paths only, as SAP documents. A prefix may be declared after the path (`/ns1:root/shop xmlns:ns1="…"`, SAP); a default namespace (`xmlns="…"`) is rejected, as CPI does. Steps without a prefix take the prefix of the step before them, which reproduces SAP's example (matching any namespace would too: **to verify**); `\| + * > = <= [ ] @` are rejected. A trailing `/` is accepted (seen in real iFlows). Split points under different parents get a warning: SAP supports relative paths only for split points on the same level and recommends naming the parent, but documents the result, which the simulator reproduces. `${header.x}` and `${property.x}` in the XPath or grouping are resolved first. No match gives no message (SAP: the flow ends as *Completed*). |
| Split messages | General Splitter messages start with `<?xml version='1.0' encoding='UTF-8'?>`, as in SAP's example; Iterating ones have no declaration (SAP's examples show none). Attribute order can differ from the input (the JDK's DOM). `CamelSplitIndex`, `CamelSplitComplete` and `CamelSplitSize` (only on the last message with streaming, SAP) are shown, not set. Parallel processing, timeouts and *Stop On Exception* are not simulated. |
| JSON to XML converter | SAP's conversion rules and limitations (S30): `@` members are attributes and must come first ("Trying to write an attribute when there is no open start element"), `$` is the text, arrays repeat the element, `null` gives `<E/>` and `""` gives `<D></D>` (as a tenant writes them, F56; SAP's example shows `<D/>`), numbers keep their text; the root object must have exactly one member unless *Add XML Root Element* wraps it; a top-level array, `{}`, `"@x": null`, an attribute as root and names that are no valid XML names (SAP's naming rules) are errors with SAP's wording where SAP gives it. With namespace mapping, mapped prefixes become XML prefixes declared on the root; an unmapped prefix keeps the full member name (SAP's rule). Without namespace mapping `"abc.A"` stays `<abc.A>`, as SAP's rule says and a tenant does (F56); SAP's example shows `<A>`. Output: SAP's declaration `<?xml version='1.0' encoding='UTF-8'?>` and no indentation, as on a tenant. Several root members with *Add XML Root Element*, arrays inside arrays and the root element's namespace (a prefix of the Namespaces tab) are **assumptions** or `UnsupportedInSimulator`. |
| XML to JSON converter | SAP's rules and examples, matched exactly in the tests: all values are strings; `@` attributes, then children, then `$` for text; an empty element is `""`; whitespace between elements is ignored, a whitespace value is kept; comments and processing instructions are dropped; mixed content gives SAP's documented wrong result (with a warning). Without streaming, siblings of a name become one array (their order among other siblings is lost); with streaming, *All* or the listed paths become arrays and other repeated elements become duplicate members (SAP's documented invalid JSON, with a warning). A listed element that repeats after other siblings starts a second array, also a duplicate member (an **assumption**, with a warning). Namespaces: mapped namespace → JSON prefix, else the XML prefix, else SAP's exception (streaming ignores the namespace); without mapping, local names. *Suppress JSON Root Element* as in SAP's special cases. JSON output encoding from the step or `CamelCharsetName`, else UTF-8. Compact output and JSON escaping (non-ASCII and `/` unescaped) match a tenant's response to the probe (F54). |
| XML to CSV converter | SAP's example is reproduced: one row per source element (its simple child elements in document order, attributes first with *Include Attribute Values*), an *XML based* header from the first record's names, and with *Include Parent Element* the parent's header and values on lines of their own before the records. As a tenant answered the probe (F55), an empty line follows the parent's lines (SAP's example shows none), every line ends with a line break, the last one too, and values are written as they are: no quoting, also for a separator or a `"` in the value (a warning for the separator). A path without leading `/` starts at the root (SAP's example). Child elements with children raise `UnsupportedInSimulator` (SAP supports simple types only). **Assumptions:** the line break is `\n` (the tenant's response was seen in a viewer); *XSD annotation based* headers are not simulated. |
| CSV to XML converter | SAP's two examples are reproduced (element order from the XSD, columns matched to XSD elements by the header line, the record marker as a row's first value, columns not in the XSD ignored); without a header line the values go to the XSD elements in order and a marker column is skipped (SAP). *CSV Fields Sequence* assigns the values by position as well, as *Use the CSV to XML Converter* describes it; *Configure CSV to XML Converter* words it as "the order of output XML elements to match the CSV fields sequence", which could also mean elements named by the header line in CSV order. The simulator follows the example page (an **assumption**). The XSD is read from the project (`xs:sequence`, `xs:all`, `xs:choice`, named types and element references; other content models raise `UnsupportedInSimulator`); `${header.x}` / `${property.x}` in schema, path and marker are resolved first; schemas from the Partner Directory are `UnsupportedInSimulator`. As a tenant answered the probe (F56): compact output with SAP's declaration and no final line break (SAP's example is indented), double-quoted fields lose their quotes (RFC 4180), empty lines are skipped, an empty value is `<Name></Name>`. **Assumptions:** `""` inside a quoted field is a quote, a missing column leaves the element out, the prefix `ns0` for a target namespace. Which elements carry it follows the XSD rules: global declarations (also through `ref`) are qualified, local ones by `form`, else `elementFormDefault`. |
| Gather | Combine writes SAP's multi-mapping format exactly as SAP's result example: `<?xml version='1.0' encoding='UTF-8'?><multimap:Messages xmlns:multimap="http://sap.com/xi/XI/SplitAndMerge">`, all bodies in `Message1` for XML (Same Format), one `MessageN` each for XML (Different Format); each body without its XML declaration. Concatenate joins plain text bodies. Combine at XPath has no example in SAP's docs: the nodes the source XPath selects in every message replace those of the first message, under the target node (by default the source's parent); with a General Splitter's messages this rebuilds the document, as SAP's Composed Message Processor pattern describes. This is an **assumption**. Headers and properties are not aggregated (SAP), so the Gather step takes bodies only; *Use as input* leaves the input pane's headers and properties as they are. Which headers CPI keeps after a Gather is not documented. Zip and Tar, and the Incoming Format *Any* that uses them, raise `UnsupportedInSimulator`; so does Combine for a message with a DOCTYPE (it would end up inside the wrapper; what CPI does is not documented). A Combine at XPath target among the gathered nodes is an error. The algorithms each Incoming Format allows follow SAP's table. |

## Groovy Script

| Area | Status |
|---|---|
| Groovy versions | Groovy 2.4.21 for 1.x and 4.0.29 for 2.x, as SAP documents (F1, F2). |
| Java version | Java 21, as a tenant runs 1.x and 2.x (F48); the app bundles a Java 21 runtime. The engine jars still start on Java 17, where JDK-dependent output (F25) and the default charset can differ. |
| Camel version | 3.14.7 for 1.x and 2.x, as on a tenant (F48). A tenant reports `3.14.7-sap-59`, SAP's own build; its patches are not known. |
| Script API v1 | The methods of SAP's published interface (`script.api` on Maven Central): body, headers, properties, attachments (`AttachmentWrapper`), SOAP headers, sizes (F29). Also the overloads with Camel 3's `Attachment`, `getAttachmentObjects` and `setAttachmentObjects`, which a tenant's 1.x message has (F49); `AttachmentWrapper` is a Camel `DefaultAttachment`, as in SAP's API jar (F30). Not offered: `getExtensionFunctions`, whose v1 type is not published. |
| Script API v2 | The methods of SAP's published interface (`script.v2.api` 4.2.2): attachments, `getHeader(name, default)`, `resetBodyStream`, exchange timestamps. ProcessDirect calls raise `UnsupportedInSimulator`. Also `getSoapHeaders`, `setSoapHeaders` and `clearSoapHeaders`, which a tenant's runtime class has (F49); that its list holds the v1 `SoapHeader` is an **assumption**. Not offered: `setProxyHandler`, whose type is not published. |
| Message log | `messageLogFactory` and `MessageLog` follow SAP's published interface; MPL disabled gives `null`. |
| Script context | The variables a tenant binds (F49): `messageLogFactory` and `javax.script.filename` (the script's file name, an **assumption**), and on 1.x `log` and `logger`. On a tenant these are SAP's internal `com.sap.it.script.logging.impl.ScriptLogger` (F53), whose methods are not published: `log.info(…)` and the other level methods print to the console with a note, `isDebugEnabled()` and its siblings answer true (an **assumption**); other calls raise `UnsupportedInSimulator`. `fingerprint-v1.groovy` now lists the logger's methods. `println` goes to the console. |
| Runtime defaults | Timezone `Etc/UTC` and locale `en_US` in every engine, as on a tenant (F48), whatever the computer uses; UTF-8 is Java 21's default charset. |
| Platform APIs | Follow SAP's published `generic.api` (F33): Secure Store (user credentials, OAuth2 tokens from a fixed value), Value Mapping (`getMappedValue`), Partner Directory (parameters, certificate parameters, partner IDs, authorized users, deprecated pattern lookups), Keystore (keys, certificates, chains, key pairs, key and trust managers), number ranges. Other services raise `InvalidContextException`. For names that do not exist, the results and messages match a tenant (F52); the simulator adds where it looks (e.g. `platform/credentials.json`). Without `platform/keystore.json` the Keystore is empty: lookups return null, as for an unknown alias on a tenant, and the run notes it. |
| Data Store from scripts | Not simulated: CPI has no public script API for it (F28). |
| Scripts of a Message Mapping (custom functions) | A function runs on its own with arguments: `MappingContext` (headers, properties) and `Output` follow SAP's Javadoc (F40). The signature picks the execution type, as community guides describe CPI (F44): a single-value function (`String` arguments) is called once with one value per argument (CPI, per these guides, calls it once per value); a `String[]` function is *All values of a context*: one call per context, without context changes in its arrays (F42), each call with its own `Output`, the results joined by context changes (an **assumption**). According to the same guides CPI has no *All values of a queue*; this is **to verify** (Q-M1). SUPPRESS and xsi:nil are the simulator's own marker strings. The Groovy version behind mapping scripts is **to verify** (Q-M1); SAP says Groovy Script 2.x is not supported in Message Mappings (F41), so 2.x runs warn. The mapping itself (`.mmap`) is not simulated. |
| Extra libraries on the class path | The libraries a tenant offers, in the versions it reports (F50, F53): commons-lang3 3.20.0 on 1.x and 2.x, Jackson databind 2.21.7 and commons-codec 1.16.1 on 1.x, Camel's `org.apache.camel.attachment` 3.14.7 on both. Not bundled: IAIK (a commercial library) and the Camel 2 class `org.apache.camel.Attachment` a tenant still has; scripts can add jars to `lib/`. |
| Groovy modules on 2.x | xml, json, dateutil, datetime, templates, nio, yaml and toml, as on a tenant (F50). The Jackson and SnakeYAML classes yaml and toml need are moved to other package names, so 2.x scripts cannot load Jackson, as on a tenant. Not simulated: the SAP classes `com.sap.it.script.v2.api.Exchange` and `…language.SimpleBuilder`, which a tenant's 2.x scripts can load (their behaviour is not published). |
| Pretty-printing (`XmlUtil.serialize`) | Depends on the JDK version (F25), so byte-exact comparisons depend on the Java version (a tenant runs Java 21, F48). |
