# Fidelity: what matches CPI and what does not (yet)

"To verify" means the behaviour follows SAP's documentation or Camel's code but has not been
observed on a tenant. The probes in [`probes/`](../probes/README.md) turn these items into facts.
Finding numbers (F…) and questions (Q…) refer to the [plan](plan.md). Tenant observations are from
one tenant and date, not a guarantee for every tenant or later runtime. This page describes the
current checkout; the [changelog](../CHANGELOG.md) distinguishes released and Unreleased changes.
Browser HTTP upload and queue limits and [project path containment](architecture.md#engines-and-protocol)
are Workbench settings and checks, not CPI step behaviour. Missing local engine profiles are reported
per Flow Step configuration; this is not a CPI runtime requirement. The local importer also imposes
[archive size and entry limits](project-files.md#project-layout), not tenant export limits.

Each row says what it **applies to** (the app's step ids: `xslt`, `xsd`, `xpath`, `groovy`, `mapping`,
`contentModifier`, `filter`, `router`, `splitter`, `gather`, `converter`, `encoder`, `decoder`, `messageDigest`)
and its **basis**, the weakest claim in the row:

* **Tenant**: seen on a tenant (an F number with a probe).
* **Documented**: follows SAP's documentation or Camel's / Saxon's behaviour, not seen on a tenant ("to verify").
* **Assumption**: neither documented nor observed.
* **Not supported**: the simulator refuses it (`UnsupportedInSimulator`) or a known gap.

The app shows these per step (the weakest of Tenant, Documented and Assumption, with all rows on a click), read
from this page when it is built; `app/tests/fidelity.test.mts` checks that every row has both. When a probe's
result comes back, change the row's basis together with its text.

The steps (SAP: *Define Content Modifier*, *Define Filter*, *Define Router*, *Define General Splitter*, *Define Iterating Splitter*, *Define Gather and Join*):

| Area | Applies to | Basis | Status |
|---|---|---|---|
| XPath | contentModifier, router, filter | Assumption | Saxon-HE 9.9 (CPI's release line; Saxon 12 if 9.9 is not installed), XPath 3.1, in the XML engine: SAP documents XPath 3.1 for the Content Modifier, and Router conditions in real iFlows use XPath 2.0 syntax such as `/node()/*:IDOC` (F37). Namespace prefixes come from the namespace mapping (the iFlow's *Runtime Configuration*), shared with the XPath tab. The Router's XPath version is not documented; 3.1 is an assumption. |
| XPath variables | contentModifier, router, filter | Documented | `$name` is the header of that name, else the exchange property: Camel's XPath variable resolver (`MessageVariableResolver` in Camel 3.14.7) does this, and real iFlows rely on it (`Student[Age > $AgeLimit_Header]`, `$NodeId="0"`; F39). Typed values (Integer, Boolean, …) become typed XPath values. Applies to Content Modifier XPath rows, Router XML conditions and the Filter. |
| Content Modifier rows | contentModifier | Assumption | Run top to bottom (SAP); the header table before the property table, both before the body (SAP Community blog, seen only in a search summary: **to verify**). An XPath row reads the incoming body; with `$name` it sees the headers and properties of the rows above it. The simulator evaluates each row once on the same Camel exchange and stops on the first error. Constant values are not evaluated. *Data Type* is resolved by Camel, so `String` works as well as `java.lang.String`; a DOM type (`org.w3c.dom.NodeList`) keeps the XML as text. An XPath that returns several items gives the first one's string value: **to verify**. An empty body field leaves the body as it is: SAP does not say so, but most of SAP's sample Content Modifiers only set headers or properties and have an empty body (F38), which would otherwise erase the payload (an **assumption**). The simulator preserves binary input as bytes in this case; decode compressed data first if a row needs to read it as XML or text. On binary input, an Expression row reading `${body}` without *Data Type* gives the body's `byte[]`, as Camel's Simple language does: an **assumption** (Camel's behaviour, not checked on a tenant). A body Expression, or a row with *Data Type* `java.lang.String`, turns the bytes into text with the message charset (`CamelCharsetName`, else UTF-8); Camel replaces bytes that are not valid text with U+FFFD, and the simulator then warns. That CPI replaces them the same way is an **assumption**. The body is Constant or Expression; Content Modifiers up to version 1.3 have no type and their body is an expression (F38). |
| Content Modifier sources the simulator lacks | contentModifier | Not supported | Local and global variables: no variable store, so the *Default Value* is used, as CPI does when the variable is not found. Number Range and External Parameter: `UnsupportedInSimulator`. |
| Delete rows | contentModifier | Assumption | The iFlow stores `$name=X` or `$include=pattern,$exclude=pattern` (F36); Camel's `removeHeaders` / `removeProperties` apply the patterns. That CPI uses these Camel methods is an assumption. |
| Filter | filter | Assumption | XPath 3.1 (SAP: Filter 1.1 uses XPath 3.1 EE); the result becomes the body, headers and properties stay. String joins the string values of all items (SAP's example: `10010`); Integer is that text as a whole number; Boolean is the effective boolean value; Node the first node; Nodelist all nodes one after another without a wrapper (SAP's examples). Integer, Boolean and Node follow Camel's XPath result types and the join has no separator (Camel's converter): **assumptions**. `function:simple('${…}')` (SAP's example) is replaced by the value Camel Simple gives, as an XPath string; that CPI treats it as a string is an assumption. Call-like text in the returned value (`function:simple(...)` inside the substituted string literal, or in an XPath comment) stays literal and is not evaluated again; so does call-like text in the XPath's own string literals and comments. |
| Router | router | Assumption | Conditions run in the order of the gateway's outgoing flows in the iFlow (an assumption; the model has no order field), and the first true one wins. Routes that mix XML and Non-XML conditions are an error: SAP says the evaluation then fails. Without a match the default route is taken. With *Throw Exception* the simulator raises an exception instead; SAP only says that the default route must then end with *Terminate Message*, so this is an **assumption**. A condition that fails to evaluate is shown as an error. |
| General Splitter | splitter | Documented | Each message keeps the envelope of the **first** split point: its ancestors and, on every level, the siblings before it. Later siblings are dropped, and every split point goes under the first one's parent. This reproduces all of SAP's examples (`SplitStepTest`); other cases are inferred from them. |
| Iterating Splitter | splitter | Assumption | Each message holds only the split point(s); with grouping above 1 they are concatenated (an assumption). *Token* splits at elements with that local name (CPI may use Camel's text-based `tokenizeXML`: **to verify**). |
| Line Break | splitter | Documented | General puts the first line in front of every message (SAP); Iterating does not. Like SAP's example, the text `\n` also counts as a line break. Messages have no trailing line break (**to verify**). |
| Splitter XPath | splitter | Documented | Paths only, as SAP documents. A prefix may be declared after the path (`/ns1:root/shop xmlns:ns1="…"`, SAP); a default namespace (`xmlns="…"`) is rejected, as CPI does. Steps without a prefix take the prefix of the step before them, which reproduces SAP's example (matching any namespace would too: **to verify**); `\| + * > = <= [ ] @` are rejected. A trailing `/` is accepted (seen in real iFlows). Split points under different parents get a warning: SAP supports relative paths only for split points on the same level and recommends naming the parent, but documents the result, which the simulator reproduces. `${header.x}` and `${property.x}` in the XPath or grouping are resolved first. No match gives no message (SAP: the flow ends as *Completed*). |
| Split messages | splitter | Documented | General Splitter messages start with `<?xml version='1.0' encoding='UTF-8'?>`, as in SAP's example; Iterating ones have no declaration (SAP's examples show none). Attribute order can differ from the input (the JDK's DOM). Line breaks are LF on every computer (the JDK's XML writer would use CRLF on Windows). `CamelSplitIndex`, `CamelSplitComplete` and `CamelSplitSize` (only on the last message with streaming, SAP) are shown, not set. Parallel processing, timeouts and *Stop On Exception* are not simulated. |
| JSON to XML converter | converter | Assumption | SAP's conversion rules and limitations (S30): `@` members are attributes and must come first ("Trying to write an attribute when there is no open start element"), `$` is the text, arrays repeat the element, `null` gives `<E/>` and `""` gives `<D></D>` (as a tenant writes them, F56; SAP's example shows `<D/>`), numbers keep their text; the root object must have exactly one member unless *Add XML Root Element* wraps it; a top-level array, `{}`, `"@x": null`, an attribute as root and names that are no valid XML names (SAP's naming rules) are errors with SAP's wording where SAP gives it. With namespace mapping, mapped prefixes become XML prefixes declared on the root; an unmapped prefix keeps the full member name (SAP's rule). Without namespace mapping `"abc.A"` stays `<abc.A>`, as SAP's rule says and a tenant does (F56); SAP's example shows `<A>`. Output: SAP's declaration `<?xml version='1.0' encoding='UTF-8'?>` and no indentation, as on a tenant. Several root members with *Add XML Root Element*, arrays inside arrays and the root element's namespace (a prefix of the Namespaces tab) are **assumptions** or `UnsupportedInSimulator`. |
| XML to JSON converter | converter | Assumption | SAP's rules and examples, matched exactly in the tests: all values are strings; `@` attributes, then children, then `$` for text; an empty element is `""`; whitespace between elements is ignored, a whitespace value is kept; comments and processing instructions are dropped; mixed content gives SAP's documented wrong result (with a warning). Without streaming, siblings of a name become one array (their order among other siblings is lost); with streaming, *All* or the listed paths become arrays and other repeated elements become duplicate members (SAP's documented invalid JSON, with a warning). A listed element that repeats after other siblings starts a second array, also a duplicate member (an **assumption**, with a warning). Namespaces: mapped namespace → JSON prefix, else the XML prefix, else SAP's exception (streaming ignores the namespace); without mapping, local names. *Suppress JSON Root Element* as in SAP's special cases. JSON output encoding from the step or `CamelCharsetName`, else UTF-8. Compact output and JSON escaping (non-ASCII and `/` unescaped) match a tenant's response to the probe (F54). |
| XML to CSV converter | converter | Assumption | SAP's example is reproduced: one row per source element (its simple child elements in document order, attributes first with *Include Attribute Values*), an *XML based* header from the first record's names, and with *Include Parent Element* the parent's header and values on lines of their own before the records. As a tenant answered the probe (F55), an empty line follows the parent's lines (SAP's example shows none), every line ends with a line break, the last one too, a value that contains the separator is put in double quotes (`a;b` → `"a;b"`), quotes inside a value are not doubled (`"quoted"` stays `"quoted"`, F57); that a value with both only gets the outer quotes is an **assumption**. A path without leading `/` starts at the root (SAP's example). Child elements with children raise `UnsupportedInSimulator` (SAP supports simple types only). **Assumptions:** the line break is `\n` (the tenant's response was seen in a viewer); *XSD annotation based* headers are not simulated. |
| CSV to XML converter | converter | Assumption | SAP's two examples are reproduced (element order from the XSD, columns matched to XSD elements by the header line, the record marker as a row's first value, columns not in the XSD ignored); without a header line the values go to the XSD elements in order and a marker column is skipped (SAP). *CSV Fields Sequence* assigns the values by position as well, as *Use the CSV to XML Converter* describes it; *Configure CSV to XML Converter* words it as "the order of output XML elements to match the CSV fields sequence", which could also mean elements named by the header line in CSV order. The simulator follows the example page (an **assumption**). The XSD is read from the project (`xs:sequence`, `xs:all`, `xs:choice`, named types and element references; other content models raise `UnsupportedInSimulator`); `${header.x}` / `${property.x}` in schema, path and marker are resolved first; schemas from the Partner Directory are `UnsupportedInSimulator`. As a tenant answered the probe (F56): compact output with SAP's declaration and no final line break (SAP's example is indented), double-quoted fields lose their quotes (RFC 4180), empty lines are skipped, an empty value is `<Name></Name>`. **Assumptions:** `""` inside a quoted field is a quote, a missing column leaves the element out, the prefix `ns0` for a target namespace. Which elements carry it follows the XSD rules: global declarations (also through `ref`) are qualified, local ones by `form`, else `elementFormDefault`. |
| Gather | gather | Assumption | Combine writes SAP's multi-mapping format exactly as SAP's result example: `<?xml version='1.0' encoding='UTF-8'?><multimap:Messages xmlns:multimap="http://sap.com/xi/XI/SplitAndMerge">`, all bodies in `Message1` for XML (Same Format), one `MessageN` each for XML (Different Format); each body without its XML declaration. Concatenate joins plain text bodies. Combine at XPath has no example in SAP's docs: the nodes the source XPath selects in every message replace those of the first message, under the target node (by default the source's parent); with a General Splitter's messages this rebuilds the document, as SAP's Composed Message Processor pattern describes. This is an **assumption**. Headers and properties are not aggregated (SAP), so the Gather step takes bodies only; *Use as input* leaves the input pane's headers and properties as they are. Which headers CPI keeps after a Gather is not documented. Zip and Tar, and the Incoming Format *Any* that uses them, raise `UnsupportedInSimulator`; so does Combine for a message with a DOCTYPE (it would end up inside the wrapper; what CPI does is not documented). A body that is not a well-formed XML document (JSON or text from a script) is put into Combine's result as it is, with a warning. The result is checked on its own: JSON or plain text inside the wrapper is character data and the result stays well-formed, while text such as `a & b` makes it malformed, which a second warning says. What CPI does is not documented (**assumption**, Q-F1, probe `probes/gather/`). A Combine at XPath target among the gathered nodes is an error. The algorithms each Incoming Format allows follow SAP's table. |
| Encoder and Decoder | encoder, decoder | Assumption | *Base64 Encode* / *Decode*, *GZIP Compress* / *Decompress*, *ZIP Compress* / *Decompress* (F63), after Camel 3.14.7's data formats with their defaults (F64). **Assumption:** that CPI's steps are those data formats; not probed on a tenant (Q-E1). Then: Base64 Encode writes lines of 76 characters, each ended by CR LF, the last one too (SAP's example, 60 characters, is one line with CR LF after it in that reading); Base64 Decode skips characters outside the alphabet (with a warning, which Camel does not give), stops at the first `=` and never fails. GZIP writes no name, time 0 and OS 255; its compressed bytes depend on the JVM's zlib. ZIP Compress writes one entry named after the file name part of `CamelFileName` and sets `CamelFileName` to that name with `.zip`; without the header Camel takes the message id, and the simulator makes one up (with an info). ZIP Decompress takes the first entry, sets `CamelFileName` to its name and fails with Camel's message on a second entry. A result that is no text (not decodable, or with a NUL character) is passed on as bytes (`bodyBase64`); a Groovy script gets such a body as `byte[]` (which class a tenant gives it is not known), and a script's own binary result is shown as text with an `UnsupportedInSimulator` warning. Unpacking stops at 128 MB (`UnsupportedInSimulator`). MIME Multipart is `UnsupportedInSimulator`. |
| Message Digest | messageDigest | Assumption | SAP's settings (F63): filter XPath, the six canonicalization methods or *None*, MD5 / SHA1 / SHA256 / SHA384 / SHA512, the target header (default `SAPMessageDigest`) with the Base64-encoded digest; the body stays. A body that is not XML fails with a canonicalization method. |

## Local workflow and CPI Helper

These are simulator features and safety rules, not CPI runtime behaviour.

| Area | Status |
|---|---|
| CPI Helper links | Reads the undocumented GroovyDebugX/xsltDebugX JSON + raw DEFLATE + Base64url formats (S47, Q-T2). Windows imports were tried with tenant messages. Contiva's format is unsupported. |
| Desktop receiver | Opt-in loopback page, Host/Origin checks and bounded requests; confirmation before import. No tenant connection. Any page can open a link, so origin checks do not authenticate CPI Helper as sender. |
| Project editor saves | Save acknowledges only the text sent to the engine. Edits made during the write stay unsaved; a response for a closed or replaced document does not change the current editor. New file destinations use an exclusive filesystem create and require confirmation on a conflict, independent of the file tree. |
| Project context | The desktop UI and each browser tab send their selected project with each request, including the first after a worker restart. An unavailable folder is an error, not a fallback to another project or to empty defaults. The failed operation is not replayed. |
| Code execution on import | Incoming scripts/mappings never execute automatically. Receiver imports also disarm already-open code, including body-only imports and pending Live callbacks. Pasted/browser-mode body-only imports may re-run existing armed code with Live on. |
| Body warnings and limits | Compressed links stop at 128 million UTF-16 code units after unpacking. XML/JSON-like bodies up to 64 million are checked with the webview's XML parser or `JSON.parse`; warnings do not establish that the trace was truncated or that a script will fail. Above that size no body parse check runs. Node tests lack `DOMParser`; browser error structures are engine-specific. |
| iFlow steps with settings left out | A Filter, Splitter, Gather, Encoder, Decoder or Message Digest from an iFlow whose export lacks one of its choices (value type, splitter or expression type, message type or algorithm, scheme, canonicalization, digest algorithm, target header) runs with the Flow Steps tab's default for it. Whether CPI uses the same default is an **assumption**; the app shows the line *Not in the iFlow, so the default is used* and the MCP server returns `step.defaulted`. |
| Remaining verification | Full plugin-click acceptance, macOS receiver/WKWebView and Local Network Access restrictions remain manual checks. The origin of the observed cut-off trace body is open (Q-T3). |

| Platform APIs | groovy | Documented | Follow SAP's published `generic.api` (F33): Secure Store (user credentials, OAuth2 tokens from a fixed value), Value Mapping (`getMappedValue`), Partner Directory (parameters, certificate parameters, partner IDs, authorized users, deprecated pattern lookups), Keystore (keys, certificates, chains, key pairs, key and trust managers), number ranges (`min`, `max`, `next`, `fieldLength` as whole numbers within a long, read exactly; anything else is an error naming the field, a check of the simulator's file format, not CPI behaviour). Other services raise `InvalidContextException`. For names that do not exist, the results and messages match a tenant (F52); the simulator adds where it looks (e.g. `platform/credentials.json`). Without `platform/keystore.json` the Keystore is empty: lookups return null, as for an unknown alias on a tenant, and the run notes it. |
| Value Mapping and package import | groovy | Assumption | An exported Value Mapping (F65) becomes rows of `platform/value-mappings.json`, one per direction of each group, because SAP calls a value mapping a bi-directional lookup table (S52). Rows towards an entry marked default come first, so a lookup from a value that maps to several gives the default: a reading of SAP's documentation, **not observed on a tenant**. Without a default the first group in the file wins (**assumption**; the import says how many such values there are). A package export (F66) is unpacked artifact by artifact; script steps find scripts of a script collection that is in the project. Both formats are read from one export each (best effort). As a simulator safety policy, package artifacts whose folder names collide after sanitization (also ignoring case and trailing dots, for Windows portability) are rejected before any files or value mappings are written, with or without overwrite; so is a folder that differs from an existing one in `iflows/` only in case or trailing dots. |
| Data Store from scripts | groovy | Not supported | Not simulated: CPI has no public script API for it (F28). |
| Scripts of a Message Mapping (custom functions) | mapping | Assumption | A function runs on its own with arguments: `MappingContext` (headers, properties) and `Output` follow SAP's Javadoc (F40). The signature picks the execution type, as community guides describe CPI (F44): a single-value function (`String` arguments) is called once with one value per argument (a tenant calls it once per value, F60: run it once per value to see each result); a `String[]` function is *All values of a context*: one call per context, without context changes in its arrays, each call with its own `Output`, the results joined by context changes, as a tenant showed (F59, F60). According to the same guides CPI has no *All values of a queue*. Context change, SUPPRESS and xsi:nil are strings with the texts of a tenant's `ResultList` constants (`__cC_`, `_sUpPresSeD_`, `_!xSi#NiL$_`, F60), compared by identity (an **assumption**). An empty context (`[]`) gives a call with an empty array, as on a tenant (F61). A tenant runs mapping scripts on Groovy 2.4.21 and Java 21 (F59), as the 1.x engine does; SAP says Groovy Script 2.x is not supported in Message Mappings (F41), so 2.x runs warn. The tenant's `MappingContext` also has an undocumented `invalidateCache()` (here a no-op with a note) and its `Output` a `getResultList()` that returns SAP's internal `ResultList` (here `UnsupportedInSimulator`). The mapping itself (`.mmap`) is not simulated. |
